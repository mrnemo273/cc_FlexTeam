This page translates the six stakeholder commitments into experience architecture. The profile became a hub. The hub feeds search, deliverables, content, team pages, and the brand. Mapping the flow is how we decide what to build, in what order, and what data the system needs to hold for any of it to work. The diagrams here are for alignment with the broader team — designers, BD, marketing, leadership. The next layer (visual design) lives in Wireframes (section 10).

At a glance

Four expressions. Four sitemaps. Four journeys. One data model.

What this page resolves

  1. The profile is not one thing. It's four named expressions — Profile, Card, Bio Module, Pill — all sourced from the same data. Detail 01 wireframes each one; Detail 02 shows how the Bio Module gets assembled into a tracked deliverable; Detail 03 shows the four cold-inbound front doors that bring clients to a Profile. Naming clears confusion that's been quietly tripping every other discussion.
  2. The profile is intimately connected to search. Conversational, traditional, and SEO/GEO. Every diagram here treats search as the front door, not a back-end concern.
  3. The data model splits cleanly. Roughly 14 fields the Chameleon writes; ~18 fields the system derives or saves for them. The inventory below makes the split concrete.
  4. Build order falls out of the architecture. Phase 1 ships when the data repository + the public page + the Smart Deliverable Creator are in place. Everything else (Content Opportunities, Build-a-Team, who's-available) is downstream of those three.

What stays unresolved (for now)

  1. Privacy boundaries inside the radical-transparency layer. Can peer Chameleons see “currently named on 7 SOWs”? BD yes; peers TBD.
  2. What COS gives us today vs what it needs to give us. Inventory below flags every field where current COS data is insufficient.
  3. How conversational search hands off to traditional search. Does the AI chatbot live alongside the search bar or replace it? Diagrams here show both as front doors; the choice between them is pending.
  4. Where the “who's available” page lives. Public, internal, or scarcity-framed (per stakeholder open question). Sitemap places it tentatively as a public node with the caveat that this is unresolved.

User journeys

Four perspectives. Each journey shows the entry, the steps, and what the system needs to be doing for each step to feel natural. Designed to be read alongside the sitemaps above — each step ties to a node on the maps.

Journey 01 Client · search to share
PERSONA

Marketing leader at a B2B SaaS, needs to staff a CMO role for a portfolio company

ENTRY POINT Conversational search OR cold inbound from a BD-sent Smart Deliverable link
01

Search the front door

Types a brief into the conversational search, or arrives via a Google query like “fractional CMO healthcare consultant.”

SYSTEMSearch index queries; routing to conversational or traditional view based on query shape
02

Sees 3 matched Chameleons

Conversational view returns 3 high-fit profiles with baseball-card stats and current availability. Traditional view returns a ranked SEO list.

SYSTEMMatch scoring fires on availability + industry + recent activity weights
03

Clicks into one profile

Lands on the full Profile page. Sees who they are, how they work, who they've worked with, what's recent, what other Chameleons typically pair with them.

SYSTEMPage view tracked; dwell + scroll depth + click path logged for analytics
04

Books a meeting

Either books direct (if Chameleon allows) or routes through BD per Chameleon's routing tier. The brief context from step 01 carries into the meeting.

SYSTEMRouting tier honored; conversion event fires; brief context auto-attached
05

Receives Smart Deliverable

After the discovery call, gets a live link with 1–3 tailored bios for the role. Can return any time; analytics surface back to BD.

SYSTEMLive link generated with expiration; per-Chameleon open + dwell tracked back to BD dashboard
OUTCOMEClient converts — or doesn't. Either way, every step from search to share is instrumented. The system learns which moves close.
Journey 02 Chameleon · idle to booked
PERSONA

Mid-tenure Chameleon (Sonia-archetype) coming back from a project gap

ENTRY POINT Logs into “My Chameleon” admin · first surfaces availability + active pitches
01

Flips availability switch

One click in Availability. Optional: sets a future capacity window (“20 hrs starting July 15”).

SYSTEMBucket trigger fires; promotion intensity scales with capacity declared
02

System refreshes profile

AI proposes 3 nudges — updated years count (source-date math), 2 new project logos, fresh LinkedIn posts. She accepts 2, declines 1.

SYSTEMAI propose → Chameleon approve gate; no silent overwrites of master data
03

Gets matched to a brief

Slack notification: BD sent in a brief that scored as a high fit. One-tap accept or decline. Auto-tailored bio staged for review.

SYSTEMMatch notification — replaces “raise your hand”; equal access for less-social Chameleons
04

Claims a content slot

Browses Content Opportunities board, claims a 200-word quip on AI search trends. Submits via short form. Round-up publishes a week later.

SYSTEMRepository entry; byline pills auto-created on published content
05

Sees the analytics loop

Two weeks in: profile views up 4x, deliverable share opened by 3 prospects, content quip cited in two pitches. Visible momentum.

SYSTEMAnalytics-driven feedback — visible activity replaces invisible waiting
06

Booked + flips availability off

Lands a 6-month engagement. Toggles availability off; future window auto-set for end-of-contract.

SYSTEMCycle closes; future capacity pre-populated for the 30-day-pre-contract-end window
OUTCOMEFrom idle to booked in one cycle. The work the Chameleon does is bounded (clicks, approvals, one short content piece). The rest of the loop is on the system.
Journey 03 BD · staffing · half-day to one hour
PERSONA

JCM receives a brief from a referral partner — needs 3 CD options for a healthcare brand role in the UK

ENTRY POINT Drops the brief into the Smart Staffing Dashboard · system surfaces fits in seconds, not hours
01

Drops brief into dashboard

Pastes the partner's ask. Optionally tags industry, seniority, scope. Time-to-respond: 1 hour from the client.

SYSTEMBrief logged; tokenized; sent to match scoring
02

System surfaces 4 best fits

Ranked by match score, current availability, recent activity, industry experience. JCM swaps one out for a Chameleon he knows the client will click with.

SYSTEMMatch scoring + human judgment override; auditable swap recorded
03

Chameleons opt in via Slack

Each gets a notification with brief summary. 3 of 4 accept within 20 minutes; the 4th declines. No DM thread, no chase.

SYSTEMMulti-Chameleon coordination consolidated to one tracked queue
04

Bios auto-tailored, JCM reviews

Three bios pre-tailored to the brief context. JCM tweaks two lines, approves. Smart Deliverable assembled as a live link.

SYSTEMSmart Deliverable Creator fires; tailoring uses brief context + per-Chameleon overrides
05

Live link sent + tracked

Partner receives the link in <1 hour total. Analytics show partner spent 6 min on Chameleon A's page, 2 min on B, didn't open C. JCM flags A for the meeting.

SYSTEMConversion attribution per-Chameleon; analytics feed back to all 3 involved
OUTCOMEJCM's half-day-of-Slack workflow collapses to a one-hour structured flow. The judgment stays human; the assembly is automated. Every Chameleon involved sees they were on the deliverable.
Journey 04 Marketing · content loop · multi-author piece
PERSONA

Katie runs a multi-author piece on AI search across the Collective

ENTRY POINT Posts open content slot in Content Opportunities board · 5 Chameleons claim within 48 hrs
01

Posts open slots

Opens a Content Opportunity: “What's your take on AI search? 200 words. 5 slots.” Tags topic, date, format.

SYSTEMOpportunity broadcast to Slack + admin queue; tagged for routing
02

Chameleons claim slots

5 Chameleons opt in via admin or Slack. System sends a structured form. Two also volunteer audio clips.

SYSTEMMulti-claim coordination; form submissions land directly in the round-up draft
03

Round-up publishes

Katie assembles the 5 takes into an article + 2 audio sidebars. Each contributor's byline is a pill linking to their profile.

SYSTEMByline pills auto-link to source profiles; entry added to searchable content repo
04

Loop closes

Content lands in the searchable repository. Pulled into 2 BD pitches that week. Each contributor sees the byline analytics and an attribution note on their next profile login.

SYSTEMPulled into pitches; attribution surfaced to contributor; closes the contribution → reward loop
OUTCOMEMulti-author content outperforms single-author by sharing reach. Lower friction for each Chameleon (200 words, not an essay). Same content does double duty — thought leadership + pitch material.

Data inventory — what Chameleons save vs what's saved for them

The split makes the build order obvious. Anything the Chameleon writes needs a form, an editor, and clear governance. Anything the system writes needs a source pipeline + AI nudging + accept/decline UX. The two halves are different problems.

Column 01

Chameleon writes it

~14 fields. Needs a form, an editor, AI-coaching, version history. Most Chameleons will edit at first-login and rarely after that.

  • Display name + taglineRequiredFirst-login · one-line positioning
  • Long bio (master)RequiredThe single source for every tailored child
  • Archetype selectionRequiredStrategy+Voice · Creative+Visual · Operator+Growth · Interim+Leader
  • Module configurationOptionalDefaults work for 80%; power users customize
  • Availability switchBinaryAvailable for new work: yes/no
  • Future capacity windowOptional“20 hrs starting July 15” — forward signal
  • Routing tierRequiredDirect · Vetted · Variable · Centralized
  • In-house vs consulting flagsPer work-history entryGoogle was a workplace — not a client
  • Source-date originationPer skill“Started UX in 2005” — system math forever
  • Personal block (optional)OptionalPersonality + interests; toggle on/off
  • Custom intake questionsOptionalHow they qualify a brief; demonstrates their thinking
  • Content claimsPer opportunityOpt-in to content slots Katie posts
  • Project description overridesPer pitchLocal override of central project summary
  • Manual logos + carouselCuratedPick which 5–7 logos lead
Column 02

System saves for them

~18 fields. Pipelines from COS, LinkedIn, SOWs, analytics, AI inference. Where the “maintains itself” commitment lives. Chameleon sees the result, doesn't do the input.

  • Project countFrom SOWsTotal + last-12-month rolling
  • Average project durationFrom SOWsMedian + range · surfaces specialization
  • Industry makeupFrom SOW tagsTop 3 industries by volume
  • Years in-houseAuto-calcFrom in-house-flagged history
  • Years consultingAuto-calcFrom consulting-flagged history
  • Client logo listFrom SOW tagsBrand + industry + year auto-tagged
  • Activity streamFrom LinkedIn + claimsRecent posts, articles, podcast clips, engagements
  • TestimonialsFrom approval-gated collectionIdea 29 flow · never sent without consent
  • Page view analyticsFrom trackingVisits + dwell + path + conversion
  • Deliverable analyticsFrom trackingPer-deliverable open rate + which Chameleon clicked
  • Peer endorsementsInternal-onlyUsed in admin/matching tools; not on public page
  • Currently named onMulti-pitch transparencyActive SOWs + open pitches · privacy TBD
  • Capacity-to-target sensingFrom COSHow close to revenue goal; flags availability passively
  • AI-suggested updatesAI-derived“Add this project” nudges, sourced from SOW activity
  • Match readiness scoreAI-derivedHow well the profile matches inbound briefs
  • Most-pitched skillsFrom SOW + pitch activityWhat clients are buying you for
  • Network connectionsFrom SOW co-tagsChameleons you've worked with most
  • Recommended-for-brief scoreAI-derived, per briefReal-time fit score when a brief is open

Implications + what to validate

This page makes some bets explicit. Round 2 needs to validate them; the build sequence needs to honor them; the team needs to align on them. Three groupings:

What the architecture commits us to

  • Build order is roughly fixed. Phase 1 = data repository + public profile page + Smart Deliverable Creator. Everything else (Content Opportunities, Build-a-Team, who's-available, staffing dashboard) depends on those three existing. The order isn't arbitrary — it's structural.
  • Search is the front door, not a back-end concern. Conversational + traditional + SEO/GEO all funnel into the profile system. The search experience deserves its own design pass — it's as important as the profile pages themselves.
  • The Chameleon admin is the second design surface. Without a strong admin, the data repository stays empty. Task #40 (admin wireframe) becomes higher priority after Round 2 confirms direction.
  • COS becomes a load-bearing dependency. Half the system-derived fields depend on COS data quality. If SOW tagging stays inconsistent, the system can't do its job. This is now a cross-team request, not just a profile project concern.

What Round 2 needs to validate

  • The three shapes read as one system, not three products. If Round 2 voices see them as three different things, the architecture didn't land — revisit naming and visual continuity.
  • The Smart Deliverable Creator feels natural to non-BD Chameleons. Delivery-only and Expert Network voices should react to it specifically.
  • The data-input ask doesn't feel like maintenance work. If “Chameleon writes 14 fields” reads as a burden, the AI-coaching layer needs to do more of the lift.
  • Multi-pitch transparency feels safe, not surveilling. Test the “currently named on 7 SOWs” pattern carefully — voices will reveal whether this lands as agency or as monitoring.

What this is not

This is not visual design — that lives in Wireframes (section 10). This is not the rubric-scoring of features — that lives on Ideas. This is not the decision log — that lives on Decisions. This page is the experience architecture — the connective tissue between commitments and pixels, the diagram that explains how the system works to anyone who hasn't been in the room.

How to use this page
When a stakeholder asks “how does this all fit together?” — send them here first. The sitemaps explain where things live. The journeys explain how it feels to move through. The data inventory explains what the system needs to hold. The visual design and the feature rubrics live next to this page; this is the spine that connects them.
